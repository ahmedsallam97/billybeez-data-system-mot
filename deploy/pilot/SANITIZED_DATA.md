# Sanitized pilot data

The existing deployment uses an isolated SQLite generation and employee-file directory. To prepare a **new synthetic generation**, run:

```text
node deploy/pilot/prepare-sanitized-data.cjs <absolute-new-generation-path-outside-source-workspace>
node deploy/pilot/prepare-accounts.cjs <generation-path> <new-private-credentials-file>
```

The first command initializes the committed model schema from empty, applies existing SQLite integrity migrations, and calls the existing account, settings, report and appraisal services. It does not accept an input database, read workplace data, invoke the workplace seed, reset an existing directory or create credentials for publication.

All operational examples use branch `TEST`, date `2098-06-15`, and clearly named test employees/bookings. No employee files are included. Demonstration uploads must be synthetic PNG/JPEG/PDF files. Account passwords are randomly generated by the existing private account-preparation command; keep its output outside source control. Prepared login display names must be marked `TEST ONLY`.

The demo policy is artificial and **must not be used for workplace grading**. The synthetic weights are 40% daily performance, 30% attendance, 20% recognition and 10% guest feedback. The sole process step is `TEST_CHECK`; the toy survey is `TEST_RATING`; the example reward is `TEST_PLUS_2`. No workplace processes, survey questions, scoring policy or October records are imported or published.

One independently approved synthetic trip supplies an example raw daily score of 8/10, derived daily score of 10/10, Recognition 25/100, Guest Feedback 75/100, and monthly draft score 82.5. The birthday and two linked shift reports remain drafts for rehearsal. Monthly approval and Employee of the Month workflow must still run through authorized APIs.

The output has a pilot volume marker, `sanitized-fixture.json` metadata, the database and an empty `employee-files` directory. Reuse the existing encrypted backup/restore tooling and Compose/Caddy configuration. The fixture metadata identifies the selected test date and record IDs; it contains no login credentials. Public deployment still requires owner hosting, DNS, approved region/free capacity, HTTPS and private backup destination.
